# UE 插件三份文档

从用户指定的插件根目录开始。读取 `.uplugin`、现有文档和相关模块的 `.Build.cs`，沿正常使用入口查到实现。纯内容插件从实际 Content、Config 或脚本入口取证。用户给了参考插件时，提取其标题层次、版本策略和验证记录风格，再用当前插件的事实填写。在插件根目录维护 `README.md` 和 `AGENTS.md`。查找更新记录时，先读 README 的仓库内链接，再查已有的项目级 `CHANGELOG.md`。沿用找到的位置，只维护一份。新建时使用用户或项目约定的文档目录，未指定时放在插件根目录。

## 三份文档分别回答什么

- **README.md** 面向安装者。先写插件做什么、适用的 UE 版本与平台、放到哪一层、如何启用和从哪里看到效果。需要时补充停用、迁移、公开 API、资源或依赖、源码入口、复验命令和限制。区分发行包用户与源码开发者。
- **AGENTS.md** 面向后续维护者。写出作用目录、阅读顺序、主要入口及调用关系。指出修改时要保持的约束，例如资源打包、委托清理、版本兼容或用户数据保护。用这个插件真实存在的文件名、模块和测试描述验证方式。
- **CHANGELOG.md** 面向交付与回溯。较新版本在上，记录版本、日期、实际功能或配置变更及验证范围。首次建档只有当前版本可证实时，从当前版本开始。保留已有记录的日期和结论。

## 版本同步与交付

优先采用仓库或用户指定的惯例。采用“每项独立修改递增一次版本”的工程，核对整数 `Version` 与 `VersionName`，同步 README 的版本和 CHANGELOG 的顶部条目；同一项修改后补充测试结果时记入同一条。描述文件的格式号 `FileVersion` 单独处理。仅受托整理文档且项目没有版本约定时，按已有描述文件记录当前版本。

保留已有作者的内容与措辞，对变更涉及的部分做定向更新。交付前逐个核实相对链接、入口名称、命令、依赖和版本。在记录中区分静态检查、实际模块编译、整工程构建、自动化、编辑器交互或设备验收。若某项测试未运行，直接说明已验证到哪一步。
